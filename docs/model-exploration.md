# Standalone model inspection

Current status (2026-10-30): bounded content authoring, authenticated inspection/review, learner 3D/text rendering and validated publication are implemented locally. Both inspection-only and mixed scored-course publication journeys pass. The temporary EXPLORATION_DELIVERY_UNAVAILABLE gate has been removed; earlier references below are implementation history. Standalone approved-model selection in the author UI, broader model-binding replacement, deployed/provider and physical-device acceptance remain open.

A 3d_viewer or hotspot activity has exploration.overview and exploration.hotspots. Each hotspot specifies one componentId from the course model, a title and equivalent text. Overview/text limits are 10000 characters, titles 200 characters, and hotspot count at most 100. Hotspot activities require at least one hotspot; a viewer may have none. Unknown fields, unknown/ambiguous components and duplicate component references fail validation. This contract contains no actions or scores. Model version/hash and reviewer checks still apply at publication. Publication must also validate references against the actual approved model before delivery is enabled, not only the editable draft manifest.

Modules with a bound component model expose Add model viewer activity and Add component hotspot activity. Authors edit the overview, select components and edit hotspot explanations. Adding a hotspot focuses the component selector; removal requires confirmation. Validation is visible inline and content saves through the existing autosave workflow. Imported unavailable component references are retained and reported rather than silently reassigned.

Passive inspection no longer requires simulation attempt policy or simulation completion evidence merely because it renders 3D. Scored simulation types retain those requirements. Existing certification policy validation continues to require scored evidence for certification; inspection is not a scored attempt.

Evidence: full build, pure exploration contract/schema tests and architecture checks pass. Integrated author Chrome verifies viewer/hotspot creation, component selection, description persistence, duplicate detection, cancellation/removal and focus. No learner rendering, approved-model runtime validation, physical-device acceptance or successful publication is claimed yet. Run pnpm model-exploration:validate.

## Authenticated inspection and review

GET /api/v1/enrollments/{enrollmentId}/activities/{activityId}/inspection returns only release/model IDs and the model overview/component explanations. It checks the active owned enrollment, published release and current story-node access. Component references are checked against the immutable release_model_bindings manifest and its exact version, release binding and hash, not the editable model metadata embedded in course content. It returns no scores, model storage paths or simulation rules. Existing private model asset delivery supplies the geometry separately.

The acknowledgement transaction uses the same immutable-model validation and story gate, records one content acknowledgement under concurrent retries and exposes ACKNOWLEDGED progress. Merely loading inspection content creates no evidence. Inspection-only review cannot issue a credential or create a simulation attempt. Account, organization and candidate controls precede the endpoint; methods/query fields are restricted and responses use no-store.

Restricted-role PostgreSQL/HTTP tests pass for safe projection, forged draft components, changed model hash, ownership/tenant denial, suspension, unavailable story nodes, account/candidate access, single acknowledgement and absence of attempts/credentials. The fixture seeds a synthetic release while publication remains gated, temporarily adds missing bootstrap-equivalent SELECT grants on release_model_bindings and course_story_positions, then restores them. Immutable model metadata needs only read access; enrollment/release locks protect lifecycle transitions. Full build, architecture, existing HTTP, media and enrollment regressions pass. Learner 3D inspection UI and actual publication checks remain next.

## Standalone model binding

The author model picker now offers **Bind selected model** independently of simulation creation. It requires a saved draft and explicit confirmation, preserves request identity on interrupted retries, reloads the saved course, and returns focus to Add module with guidance to add viewer/hotspot activities. Existing model bindings disable this initial-binding action; replacement is a separate remaining workflow. The existing simulation action remains available for a bound model.

POST /api/v1/course-versions/{courseVersionId}/model-binding accepts only revision, modelVersionId and confirmed:true, with an idempotency header. Author authorization and tenant resolution precede the operation. The shared draft transaction locks the current revision and approved model, derives the manifest/hash from the database, preserves all other content, returns the course to DRAFT and atomically records DRAFT_MODEL_BOUND. Concurrent identical requests replay one receipt; old receipts cannot overwrite later edits. Approval loss, foreign models, immutable courses, stale revisions and existing bindings reject. No simulation, module, activity or credential is created by binding alone.

Validation: full build; restricted-runtime database writes and HTTP checks covering approval loss, rollback, concurrency, exact content preservation, later edits, authorization, confirmation and forged fields; integrated Chrome author checks covering cancellation, interrupted retry, focus and subsequent simulation creation; architecture and course-review HTTP regressions; existing standalone inspection publication/private-delivery/passive-progress rehearsal. Fixture state inspection uses the administrator connection because the local runtime role lacks course_review_decisions read access; binding writes execute under the restricted runtime role. Browser and publication checks remain separate local rehearsals. Existing-model replacement and deployed/physical-device acceptance remain open.


## Compatible model replacement

The approved-model picker remains visible alongside an existing simulation and now offers Replace bound model for bound drafts. Confirmation explains that authored component identities, activities and scoring are preserved and new geometry needs review. Initial binding and replacement use separate retry identities; successful replacement reloads the course and restores focus. Duplicate simulation creation is disabled while a simulation exists.

POST /api/v1/course-versions/{courseVersionId}/model-replacement uses the same author-only, revision-bound, confirmed and idempotent transaction as initial binding. It requires an existing binding, reads the previous model manifest from the tenant database (not editable draft component metadata), verifies its hash and requires the same unique component ID set in the approved replacement. Existing hotspot references must remain available. Simulation identity and hash are updated without changing steps, faults, policy, scoring or activity IDs; production transform validation rejects incompatible bounds/snapping. The new revision returns to DRAFT and records DRAFT_MODEL_REPLACED with previous/new model hashes and IDs. Existing published releases are not modified.

Full build, restricted-runtime database/HTTP, integrated author Chrome, architecture and course-review HTTP checks pass. Tests cover changed component IDs, forged previous draft metadata, narrower transform bounds, audit rollback, concurrent retries, exact authored content preservation, IN_REVIEW returning to DRAFT, and later-edit preservation. The existing mixed inspection/scored-simulation publication regression also passes; it is a separate rehearsal, not a replacement-to-publication end-to-end test. Arbitrary component remapping and model fidelity/device acceptance remain open. Compatible replacement does not imply that two geometries are clinically or procedurally equivalent; normal review and publication validation still apply.

## Explicit component mapping contract

The replacement API now accepts optional componentMapping entries with exactly from/to IDs. When supplied, the mapping must cover every previous database-manifest component exactly once and every replacement component exactly once. Duplicate, missing, unknown or extra-field entries reject; equal-count one-to-one remapping is supported. Component additions/removals/merges are not silently inferred.

The shared pure remapper clones the course and changes only structural references: simulation model component IDs, component definitions, initial component-state keys, step actions, fault diagnosis/resolution actions, and viewer/hotspot component references. It retains activity/step/fault IDs, scoring, policy, variables, instructions and free text. Mapping swaps are simultaneous, not cascading string replacement. Unknown stored references reject. Replacement then validates the remapped simulation against the approved target transform rules, records the explicit mapping in the atomic audit, and returns the course to DRAFT for new review. Mapping is part of the request signature, so changed mappings cannot replay a previous result.

Pure tests cover swaps, reference coverage, text/scoring preservation, input nonmutation, malformed mappings and prototype-like IDs. Restricted-runtime database and authenticated HTTP checks cover partial-map rejection, audit rollback, durable mapping receipts, state/action/hotspot rewriting and retry identity. Full build, architecture, existing author Chrome and compatible replacement successor publication regressions pass. The author component-mapping controls and changed-ID publication-to-learner rehearsal remain next; this increment is API/domain support, not a completed no-code mapping workflow. Source text may need author revision after remapping and is intentionally not changed automatically.

## Explicit removal of unused components

Mapping entries now allow to:null to explicitly remove an old component. Missing mappings are still invalid. Removal filters the simulation model component list, component definitions and initial-state keys together. Any step action, fault diagnosis/resolution or viewer/hotspot reference to a removed component rejects the entire transaction with MODEL_COMPONENT_STILL_REFERENCED. Authors must update those references before removal; scores, instructions and activity identities are never deleted automatically. Remaining targets are unique, and additional unmapped targets retain the selection-only defaults.

The mapping UI offers Remove unused component separately from an unselected target, including when the replacement has fewer components. Its option sentinel cannot collide with a real target ID. Final confirmation states the exact number of requested removals; cancellation sends no request. API input, audit and retry signatures preserve explicit null mappings.

Pure checks cover each reference guard independently and exact unused component/state cleanup. Restricted-runtime database and authenticated HTTP checks cover rejection without revision change, audit rollback, confirmed removal and retry. Chrome checks the removal choice and exact consequence confirmation/cancellation alongside existing mapping retries. Full build, architecture and expanded successor publication regression pass. A removal-specific successor publication rehearsal remains open; physical geometry/device/deployed acceptance also remains open. Merging referenced components is still unsupported rather than silently combining behavior.


## Removal successor publication acceptance

The --removed-replacement rehearsal begins with a published scored/inspection course containing an unused assembly-root component, then creates a successor and explicitly maps that component to null while remapping the retained components. It verifies removal from the new definition and initial state, unchanged scoring, renewed review gates, remapped private inspection/model access, successful authoritative learner actions and one new credential. Exact comparisons retain the original release/hash/model binding and prior credential, including the original component. The rehearsal passes locally and is included in draft-simulation:validate.

As with other replacement modes, this uses synthetic reference metadata and controlled artifact storage. It establishes transactional/publication/learning behavior, not different-geometry visual fidelity or deployed/device acceptance. Referenced component removal and many-to-one merging remain rejected.
