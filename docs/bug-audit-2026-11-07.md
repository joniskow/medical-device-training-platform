# Bug audit: 2026-11-07

The follow-up audit confirmed two implementation defects. **Both are now fixed**, with regressions that failed before the correction and pass afterward. The original reproductions below describe the observed defects before correction. Local PostgreSQL fixtures were isolated and cleaned; the disclosure probe uses a fake marker, not a real secret.

## P1: asset state changes escape stale-worker lease fencing

The [job runner](../apps/worker/src/job-runner.ts#L191) updates the asset lifecycle before completing the job through its lease-generation fence. The [PostgreSQL lifecycle store](../packages/db/src/asset-lifecycle-store.ts#L10) checks only the asset state and tenant context, without checking the job owner or generation.

Reproduction: pause worker A inside processing; reclaim the job as worker B after the 300-second lease; release A with a REVIEW_REQUIRED result; then fail B. A moves the asset to READY_FOR_REVIEW even though its fenced job completion returns null. B cannot transition that asset to PROCESSING_FAILED. Observed final state: job FAILED, asset READY_FOR_REVIEW.

The probe uses the real PostgreSQL job and lifecycle stores. Reproduce locally with `node output/bug-audit/repro-stale-asset-lifecycle.mjs` while the existing disposable database is running. The script cleans its own unique fixtures.

Required correction: apply the asset lifecycle and job outcome atomically under the same current lease-generation check. Cover success, failure and quarantine paths, including lost leases and current-worker failure. A separate preflight ownership check would leave a race between that check and the write.

## P2: processor exception text reaches the authenticated job-status response

The [worker exception handler](../apps/worker/src/job-runner.ts#L198) persists raw exception messages. The [status projection](../apps/api/src/job-status-service.ts#L50) returns lastFailure without sanitizing the message.

A controlled processor throws an error containing an HTTPS URL and fake SAS-like signature marker. The marker survives the job store and status projection. Provider errors can include signed URLs, internal paths or connection details. This test establishes the unfiltered data path; it does not claim an actual credential was exposed. The affected response requires authenticated tenant access and is not anonymous public credential verification.

Reproduce with `node output/bug-audit/repro-error-disclosure.mjs`. This controlled probe uses the existing in-memory job adapter and actual worker/status projection.

Required correction: persist and return a stable, safe failure message and code. Keep only deliberately redacted diagnostics in restricted operational telemetry. Add a regression asserting that URL signatures and private markers do not appear in stored or returned failure projections.

## Implemented corrections and verification

- Asset finalization now updates the job outcome and asset lifecycle in one tenant transaction after acquiring the current job-generation fence. The initial PROCESSING transition also locks and validates the current job lease and asset binding. Stale workers cannot invoke quarantine I/O. Quarantine failures roll back finalization and remain retryable; scanner failures can transition back from SCAN_FAILED on retry.
- Unexpected processor exceptions now persist a fixed safe message. Both lastFailure and outcome.failure are sanitized when projecting status, including historical records, while preserving failure codes and retry metadata without mutating stored evidence.
- [Asset fencing regression](../tools/check-asset-job-fencing.mjs): 14 real PostgreSQL cases using restricted runtime credentials, including current-worker positives, stale success/failure/quarantine/unsupported results, early reclamation, quarantine/scanner recovery, cross-asset binding, retired sources and both directions of transactional failure.
- [Failure privacy regression](../tools/check-job-failure-privacy.mjs): safe stored exception and historical status projections, stable retry metadata and nonmutation. Both scripts are registered in the maintained validation manifest.

The independent reviewer reran and expanded the fencing regression and found no further confirmed defect in the reviewed corrections.
