# Render and review a lesson

The author editor saves shot plans, rough-cut manifests, timestamped corrections and acceptance in the existing course draft. Rendering is a developer CLI workflow; it does not run on an application server. Local preview files must be reopened after reloading the editor.

1. Save the instructional brief, source-linked script and shot plan. Review the direction against the cited source and check its review box. Export the lesson with **Export lesson for rendering**.
2. Create `assets.json`, keyed by immutable visual asset version IDs, with entries such as `{"media:one":{"path":"approved.png","approved":true}}`. Paths resolve relative to this JSON file. The developer must resolve these to the approved source files; the CLI does not fetch tenant assets. Missing or unsupported visuals become clearly labeled placeholders in a rough cut and block final rendering.
3. Supply reviewed recordings in `recordings.json`, keyed by scene ID: `{"scene:one":{"path":"voice.wav","transcript":"Exact scene narration.","delivery":{"rate":0.9}}}`. Transcripts and reviewed delivery metadata must match the saved scene controls; omit `delivery` only for default delivery. Changed pace, pauses, emphasis or pronunciations require a new reviewed recording and matching metadata, rather than silently reusing the old voice. Without recordings, configure `AZURE_SPEECH_ENDPOINT` and `AZURE_SPEECH_API_KEY`; the CLI requests actual Azure speech. Silent deterministic synthesis is rejected. Real audio is normalized and measured. It must fit before the scene's required observation hold; otherwise extend the scene or revise the script.
4. Build the worker and contracts, then run `node tools/render-video-lesson.mjs --draft lesson-draft.json --lesson lesson-id --output output/lesson --mode rough-cut --assets assets.json --recordings recordings.json`. Set `LESSON_FFMPEG` to a full FFmpeg build containing color, drawtext, loudnorm and libx264, and `LESSON_FFPROBE` to ffprobe. The CLI detects the existing Windows imageio FFmpeg and compositor ffprobe when available.
5. Import the emitted manifest JSON and MP4 into the author editor. The browser verifies the actual MP4 SHA-256 and exact current input revision before playback/acceptance. Listen to the complete speech and inspect motion, callouts, source fidelity and placeholders. Save timestamped corrections. Adjust scene durations here and observation holds in the shot-plan editor; assembly uses restrained clean cuts. Save the draft, then export again after revisions. Claims, citations, warnings and prerequisites remain source validated. Caption timing is proportional within actual speech duration and requires synchronization review; it is not a forced alignment guarantee.
6. After inspecting the current rough cut, accept it in the author editor and save/export that draft. Run the same command with `--mode final`. Final assembly requires current rough-cut acceptance and forbids placeholders. It reuses the same source-bound timeline, selected scene takes, narration and callouts. The final MP4, companion WebVTT (with hash), manifest and a separate `rendered-draft.json` are emitted; the source draft is never overwritten.
7. Import the final manifest and matching MP4 using the same render import controls. Then upload that exact MP4 through the existing approved-media workflow and enter its media version ID in the final review panel. Perform the independent final audiovisual review. A local render manifest is not a published or independently approved release. Source identity, actual demonstrated mechanics, pronunciation, readable labels and captions, and complete critical intervals still require human inspection. Production-input edits invalidate preview acceptance and final review by revision.

Engineering check: `node tools/check-lesson-rough-cut.mjs` requires an actual speech WAV supplied through `LESSON_RECORDED_FIXTURE`. If none is available, `LESSON_ENGINEERING_SIGNAL=1` explicitly runs signal-only decoder/compositor coverage; its passing result does not establish spoken narration or listening acceptance.

## Review and handoff boundaries

- Publication excludes the original creator and later instructional editors, including relevant source-version authors. An independent reviewer can save scorecard-only changes without becoming an instructional author.
- A source lesson with a selected corrected take cannot create variants directly: otherwise copying its original visual would silently restore the defect. First promote the corrected clip through approved media, explicitly rebind the source visual, then render and independently review that source again. Direct selected-take reuse across variant timelines remains unsupported.
- The local asset map is a trusted developer handoff, not a tenant-aware asset download service. Verify exported files and sound-review records against approved immutable assets before rendering. Application approval fields require the boolean `true`.
- Generated quotations are checked against retrieved source passages. For manually edited drafts, publication checks structure, citation membership, artifact identity and independent approval; the reviewer must still compare quoted instructions and explanations with the authoritative source.
- Caption timing is proportional to measured speech duration. Listening/synchronization, pronunciation, mechanical accuracy and representative-device readability require actual human acceptance; engineering tones cannot supply that evidence.
