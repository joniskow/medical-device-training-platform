# Independent candidate enrollment foundation

POST `/api/v1/candidate-enrollments` accepts only publicId, revision, noticeVersion and confirmed:true, plus an Idempotency-Key. The actor comes from validated authentication. This route runs after the personal-account identity/lock/verification guard and before organization selection; a caller does not need a membership. Public catalog reads and this authenticated write use different endpoints. Client-supplied learner, organization, role or sharing fields are rejected.

The notice contract is `candidate-notice.v1`; the exact display text is exported as CANDIDATE_NOTICE_TEXT from the database package. The future browser enrollment form must display that text and the current course disclosures, then obtain an explicit unchecked-by-default confirmation before submitting. No browser enrollment control is enabled by this increment.

The database function requires an ACTIVE, currently verified personal account, current ACTIVE issuer, PUBLISHED release and PUBLIC/UNLISTED availability. It rejects expired/missing verification, suspended/removed existing organization memberships and stale disclosure revisions. The private opaque routing record determines the issuer/release, never a submitted organization ID. It serializes with availability/member administration and shares the learner/release assignment lock with existing administrator assignments.

New enrollment, immutable acceptance record and audit commit together. The acceptance records exact offering revision, release hash, audience/scope/prerequisites/issuer/intended-use/accessibility/effort disclosures, displayed course title and issuer name, public ID/mode, notice version and acceptance time. It never copies private assessment content. Neither membership nor role assignment is created. Existing active enrollment is reused; suspended enrollment is never reactivated. Distinct deliberate acceptance requests can create distinct consent records for the same enrollment; retrying one request key cannot create another acceptance or audit.

Replay compares the original request signature and current account/issuer/release/enrollment state. A successful prior enrollment can be acknowledged after the course becomes private without reopening enrollment to anyone else. Suspended issuer, retired release, locked/unverified account or inactive enrollment still denies replay. Disclosure edits do not rewrite earlier consent or release evidence.

The consent table has forced user RLS and no direct runtime read/write grant. The enrollment function uses a fixed search path, revokes PUBLIC execution and restores the caller's prior user/organization context. Bootstrap grants only its execution. Enrollment and assessment source-of-truth tables retain their existing tenant boundaries.

Evidence: `tools/check-candidate-enrollment.mjs` uses the restricted runtime with synthetic verified profiles and releases. It verifies absent/expired verification, stale disclosure, rollback, concurrent duplicate acceptance, concurrent assignment versus self-enrollment, no member/role creation, immutable safe disclosure snapshots, privacy withdrawal, suspension, denied direct consent access and strict HTTP inputs before membership lookup. Authentication is controlled in this HTTP fixture; real signed identity claims are covered by separate identity/account tests, and live provider acceptance remains open.

The browser now exposes explicit candidate consent/enrollment and cross-issuer active training navigation, described below. Historical credentials when no active course remains and full deployed end-to-end acceptance remain open.


## Candidate learning access

GET `/api/v1/my-candidate-enrollments` provides a paged list of the authenticated personal account's active candidate courses across issuers, without membership lookup. Its narrow SQL reader iterates only that user's consent records and restores prior user/organization context. It checks ACTIVE account, issuer and enrollment, PUBLISHED exact release, and absence of a suspended/removed membership for that issuer. Private withdrawal of new enrollment does not remove existing course access. The list contains issuer/title and routing IDs, not manifests or assessment answers.

For an explicitly selected issuer not in the user's memberships, the API admits only enrollment reads/reading acknowledgements, assessment-session operations, the learner's credential list/issue/sharing operations and recipient-owned notices. It first confirms a current candidate enrollment, then replaces token roles with only learner. The existing services still enforce target enrollment/session/credential ownership. Assignment, authoring, organization settings, member administration, credential revocation and cross-learner selectors remain denied, including for tokens carrying operator/admin claims. Model asset/session/start routes now admit candidates through the same learning gate; model delivery independently requires an active enrollment in the exact requested release. See docs/candidate-model-access.md.

New credentials issued for enrollments with candidate acceptance default to sharing disabled in both the credential and anonymous verification projection. A narrow SQL function detects the consent under user context without exposing the consent table. The existing owner sharing endpoint enables visibility explicitly. Prior credentials are not rewritten, and ordinary assigned enrollments retain their prior default. Existing verification/account checks still govern issuance.

The expanded candidate integration test now completes a real server-scored assessment and automatic credential issuance without organization membership. It verifies owner-only enrollment reads, redacted assessment projections, hostile admin role claims, explicit credential sharing, and denial after enrollment/account/issuer/release/membership status changes, plus restoration of pooled context. These tests use synthetic published-release fixtures and controlled authentication; they do not establish browser or live-provider end-to-end acceptance. Full workspace build, assigned credential regressions and architecture checks also pass locally.


## Browser enrollment and active training

Catalog detail includes a versioned platform enrollment notice alongside the issuer disclosures. Anonymous visitors are directed to sign-in/profile creation with only a validated, thirty-minute course UUID return hint; arbitrary return URLs are rejected and sign-out clears the hint. The account page links back to the selected course. No enrollment occurs during sign-in.

Signed-in visitors must check an initially unchecked required consent box. Submission sends only public course ID, offering revision, notice version and explicit confirmation, with a stable request key for an interrupted response. It sends no organization header. Changed disclosures or unavailable access lock the form and require refresh/review; successful enrollment offers an explicit Open training action. Sharing and discovery remain separate choices.

`/candidate-training` lists the account's active candidate courses across issuers, supports paging and retry, and selects the server-returned issuer before opening the exact enrollment in the learner player. Both pages fence late responses after sign-out or identity changes. Learner deep links initialize before concurrent list/wallet requests so those responses are retained.

Evidence: `tools/check-candidate-browser.mjs` runs controlled-response Chrome exercises for consent, stable retries, stale disclosure reset, unsafe/expired return hints, private paging/error states, identity changes, late-response sign-out and real navigation to the expected issuer/enrollment destination. `tools/check-learner-browser.mjs` verifies the actual player opens a requested enrollment while retaining list/wallet rendering. Catalog, personal-account and renewal browser regressions pass. The restricted-runtime candidate integration separately verifies actual consent persistence, ownership, assessment completion and private-by-default issuance. These separate fixtures do not prove one live identity-provider/Azure browser journey.

Historical cross-issuer credential read access is now implemented independently of active training; see `docs/personal-wallet.md`. Owner sharing/QR controls in that independent wallet are now locally verified; live journey acceptance remains open.

New enrollment notice version is `candidate-notice.v2`, covering the published revision and certification requirements shown in catalog detail. The consent snapshot includes that same allowlisted summary and revision. Fresh v1 submissions require updated review; prior v1 acceptance remains immutable and replayable under current access checks. See `docs/course-availability.md`.
