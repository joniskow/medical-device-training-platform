# Course availability foundation

Organization administrators can read and update availability metadata for an exact release using GET/POST `/api/v1/releases/{releaseId}/offering`. The selected organization must be active, and current database membership plus an organization-scoped administrator role are rechecked inside the operation. Global role claims alone cannot authorize it.

No row means PRIVATE with revision zero. POST requires `confirmed: true`, an Idempotency-Key, the current revision, a reason, mode PRIVATE/PUBLIC/UNLISTED, audience, productScope, prerequisites, issuerStatement, intendedUse, accessibilityPath, and integer estimatedMinutes (1–10080). Public/unlisted settings require all six disclosure strings. Cost is fixed to free-in-MVP and the future enrollment rule is self-enrollment; these cannot be supplied or overridden by the caller. This does not evaluate prerequisites automatically or assert an accessibility path has passed acceptance testing.

The table has forced organization RLS. Runtime receives only execution of a fixed-search-path function, whose PUBLIC execution is revoked; it has no direct offering-table access. The function serializes with member administration, verifies release ownership, locks the release and offering, checks revision, and commits metadata and audit atomically. Audit includes exact release hash and disclosures. Retries with changed input conflict; successful old retries return current state without reverting later privacy changes. A retired release can be set private but cannot be opened public/unlisted. The immutable release manifest is not modified.

Public browsing is now available at `/catalog`, with disclosures at `/catalog?course={publicId}`. GET `/api/v1/catalog` lists at most 50 routing candidates per page; its opaque `after` cursor continues the scan even when current lifecycle checks remove entries. GET `/api/v1/catalog/{publicId}` accepts a public or unlisted opaque ID. Both routes are anonymous, no-store and bounded by an atomic per-address minute counter (default 60), sharing the existing counter table under a separate digest namespace. The socket address is used; deployed proxy/client-IP behavior still needs acceptance testing.

The private routing table stores only organization/release routing, a random UUID and a listed flag. Runtime cannot read it directly. A trigger updates it atomically with offering changes. Moving between modes into PUBLIC or UNLISTED rotates the ID; private mode denies all direct access. The management response returns the current publicId only for nonprivate modes. Unlisted records never participate in the catalog scan. Direct sharing is a link, not a grant of course content or learner authority.

A fixed-search-path catalog function selects a bounded routing batch and sets transaction-local organization context for each lookup. It rechecks ACTIVE organization, PUBLISHED release and current offering mode, returning only an explicit twelve-field disclosure projection. It restores the caller's previous organization context before returning. It does not return release/organization IDs, source documents, assessment keys, simulation rules, account data or raw manifests. The browser renders all issuer text with textContent and clears stale detail on refresh failures. No account bearer is sent for public catalog reads; explicit enrollment uses the authenticated candidate endpoint.

Catalog detail now also includes the versioned platform enrollment notice. Explicit browser consent/enrollment and enrollment-scoped candidate access are implemented; see `docs/candidate-enrollment.md`. Enrollment rechecks current organization/release/availability and binds accepted notices/revision to the learner without creating employee membership. Published-revision and certification-requirement detail is now implemented, as described below; candidate analytics and full deployed end-to-end acceptance remain open.

Synthetic release insertion tests this store boundary; it is not an end-to-end publication or independent enrollment acceptance test.

## Issuer availability page

Organization administrators can open `/author/course-availability` from training administration or organization settings. The page lists published releases with bounded paging, then reads the selected release's current offering. It supports PRIVATE, PUBLIC and UNLISTED, all six disclosure fields, estimated effort, an audit reason and explicit confirmation. Public/unlisted fields are required; enrollment remains free. Successful saves display the current catalog link; private saves remove it. The page explains link rotation and preserved existing enrollment progress.

Edits clear confirmation, and changing releases/reloading asks before discarding unsaved changes. Interrupted responses retain the same key for an identical body. Revision conflicts disable saving until fresh settings are loaded; access loss clears disclosures. Account/organization identity and request generations fence stale responses; sign-out clears the editor and release selection. Server-side membership/role, active issuer, immutable release and revision checks remain authoritative.

Local evidence: `tools/check-course-availability-browser.mjs` checks paged release choices, inert titles, private defaults, disclosure requirements, explicit confirmation, cancelled discard, interrupted retries, public/unlisted links, private withdrawal, revision conflicts, denied access and late-response sign-out cleanup in Chrome. Compact layout is checked at 320px; a 768px rendered screenshot was inspected. Assignment and organization-settings browser regressions, restricted-runtime offering integration, full build and architecture checks pass. These controlled browser fixtures and separate database checks do not establish live Azure acceptance or complete accessibility/device certification.


## Public certification requirements

Direct catalog detail includes `publishedRevision` from the immutable release manifest and a `certification` summary. Catalog listing keeps its existing twelve-field projection. The detail summary exposes policy version, overall score threshold, best/latest result selection, maximum attempts, cooldown/time limit, repeated-failure review threshold, credential expiration and required activity titles/kinds/pass thresholds. Activities required either explicitly or through a required module are included once. Optional content, prompts, choices, correct answers, rationales, scoring rules, component/action definitions and private identifiers are excluded. Content-completion items have no score threshold. Missing/unsupported summaries are shown as unavailable, not as a promise of certification.

A pure fixed-search-path SQL helper builds only these approved scalar fields and required-activity descriptors. Both public detail and new immutable enrollment consent use that helper. Consent also stores the published revision alongside its existing exact release hash. Existing consent is never rewritten. `candidate-notice.v2` explicitly includes review of the published revision and certification requirements. Fresh v1 requests receive a disclosure-change conflict; replay of an already accepted v1 request remains possible subject to the existing current-access checks.

The page explains standard requirements for this release, possible issuer-defined update-module treatment for eligible returning learners, and that enrollment alone does not award a credential. Local database fixtures check exact summary fields, required-module/activity selection, score values, private-content exclusion and malformed scalar rejection. Enrollment integration checks summary/revision snapshots, fresh old-notice rejection and unchanged legacy replay. Chrome checks revision, passing scores, expiration and inert activity titles. Build and architecture pass; live deployment acceptance remains open.
