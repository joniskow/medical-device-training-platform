# Course stories: implementation status

Current status (2026-10-30): no-code authoring, server-authoritative navigation, learner UI, retry restart and path diagnostics are implemented. Valid story courses can now publish after the normal review and validation checks. Stories require a versioned certification policy; required-activity bypass remains a publication error. Local saved-draft/review/publication/learning integration and separate author/learner Chrome checks pass. Deployed and physical-device acceptance, and diagnosis/fault-specific conditions, remain open. The dated sections below record the implementation history; earlier temporary publication-gate statements are superseded by this status and the publication section at the end.

## Contract

A story contains mission text, a starting node and 1–200 nodes. Each node has a stable ID, title, purpose, prerequisites, optional course activity, and up to 20 choices. Choices have an ID, learner-visible label and consequence, destination and conditions. Terminal nodes carry a success, retry or ended outcome and no outgoing choices. Retry outcomes do not create graph loops or override the existing attempt policy.

Only recorded activity completion, pass status, normalized score and attempt-count conditions are supported. Arbitrary code, queries and unknown fields are rejected. Missing/duplicate facts fail closed, including negative conditions. The server integration must derive facts for the authenticated enrollment's exact release and use the configured evidence-selection policy; browser-submitted facts must never be trusted. Condition types for diagnosis/fault-specific outcomes are not implemented yet.

Validation rejects duplicate nodes/choices, missing activity/destination references, cycles, unreachable nodes and terminal nodes without outcomes. An intersection across predecessor paths proves every successful path includes every certification-required activity. Publication derives those requirements from explicit required activities and required modules. This is a conservative structural proof: mutually exclusive conditions do not exempt a path from the required-activity rule. Every branch converging on success is checked; optional practice and non-success endings remain possible.

Projection exposes visible text and enabled choices from supplied facts. Advancing uses a choice on the supplied current node, rechecks current/destination prerequisites, and requires the bound activity to be completed. These are pure functions, not a durable session service. Story success does not award progress, certification evidence or credentials. Certification remains the independent server policy evaluator.

## Authoritative activity facts (2026-10-30)

Story fact projection now shares the deterministic attempt selector used by certification. Best/latest choice, malformed evidence detection, duplicate attempt numbers and tie ordering therefore use the same implementation. Facts include optional activities as well as required ones, with completed/passed status, normalized score and latest lifetime attempt number. Attempt count is not the reset-adjusted retry allowance. A completed failed attempt can enable a retry narrative; a story result never overrides cooldown, review, attempt-limit or certification rules.

The database helper enrollmentStoryFacts runs within a tenant transaction, derives content/release/hash/policy from the owned ACTIVE enrollment and PUBLISHED release, then reuses the existing assessment, simulation and reading-acknowledgement evidence queries. It accepts no client-supplied release, policy, result or score. Outer account/organization authorization remains the calling service's responsibility; no HTTP route has been enabled. Eligibility now calls the same extracted evidence loader; certification behavior is unchanged. Requalification certification retains its separate effective-policy evaluation; story facts describe the current published release's activities, not a prior credential's inherited evidence.

Foreign release/hash/policy/version evidence is excluded. Known activities without evidence project false completion/pass, null score and zero attempts. Malformed or ambiguous evidence omits the activity entirely, so even a negative condition fails closed. Active, expired and invalidated attempts do not count as completion or expose a score. A valid historical best result can remain selected under the published best policy.

Pure policy tests cover best/latest parity, optional reading, exact bindings, invalidation, incomplete attempts, corrupt evidence and future result timestamps. PostgreSQL publication/learning rehearsal checks completed simulation facts, foreign owner/tenant denial, enrollment suspension and attempt invalidation. Existing assessment integration passes after the evidence-loader refactor. Fixtures use administrator access with controlled authentication/storage; restricted-runtime story-specific acceptance remains outstanding. Parallel database fixture setup initially deadlocked on migrations; both terminal failed runs were rerun sequentially and passed after fixing the enrollment/course-version join. Future migration-bearing checks should run sequentially.

Durable position, idempotent choices, activity launch gates, author UI, learner navigation and deployed acceptance remain open. The story publication gate remains in place.

## Durable story position and choices (2026-10-30)

The private createCourseStoryStore provides get and choose operations using a tenant transaction. It locks the owned active enrollment and published release, validates the immutable story against current course/policy references, initializes one position per enrollment, and verifies learner/release/hash binding on every call. Position includes a monotonic revision. New choices require the exact revision and an available choice at the persisted node; all facts are re-read server-side. Choice requests accept only revision, choiceId and requestId.

Accepted transitions atomically update position, insert a request receipt and add STORY_CHOICE_ACCEPTED audit evidence. Enrollment locking serializes concurrent transitions. The receipt signature binds actor, release/hash, revision and choice; identical retries return the original acceptance receipt without rewinding later progress, while changed payloads fail. Current ownership, enrollment status and release status are checked before returning any receipt. Receipts deliberately omit projected availability: clients must get current state after acceptance or replay. An old receipt does not assert that its destination is still the current node.

New tables force tenant RLS. Deployment bootstrap grants SELECT/INSERT/UPDATE on positions and SELECT/INSERT on receipts; runtime cannot update or delete receipts. No credential or learning-completion event is emitted. A story success outcome is navigation state, not certification evidence. Previous navigation is not rewound when activity evidence later changes; current availability is recomputed on reads/choices and certification eligibility remains separately evaluated. Activity-launch gating and HTTP account/organization authorization are still pending and no public route is exposed.

`tools/check-course-story-store.mjs` passes under the non-owner local runtime role: resume, concurrent identical retry, competing revisions, authoritative reading gate, injected audit rollback, immutable receipts, old retry non-rewind, forbidden request fields, tenant/owner denial, suspension/retirement/hash changes, assessment-gated terminal outcome and absence of credentials. Fixtures directly seed synthetic published content and assessment evidence because story publication remains disabled; they are not a published author-to-learner journey. The test temporarily adds missing bootstrap-equivalent grants and restores them, then removes only its fixture records. Full build and architecture checks pass.

Remaining integration: HTTP routes and authorization; activity start/acknowledgement gates; author UI and preview; learner navigation/resume and retry behavior; conditional path diagnostics; deployed acceptance. The publication gate must remain until the delivery journey is verified.

## Authenticated story routes (2026-10-30)

GET /api/v1/enrollments/{enrollmentId}/story returns the current mission/node projection and revision. POST /api/v1/enrollments/{enrollmentId}/story/choices accepts only JSON revision and choiceId plus an Idempotency-Key header. The entrypoint injects the PostgreSQL store. No request can provide a learner, release, destination node, request-body idempotency key or activity facts. Unknown query parameters are rejected. Methods, media type and required fields are validated; responses use the existing no-store writer. Conflict responses cover stale revisions, changed request payloads, unavailable choices and changed release binding; internal failures are sanitized.

Routes pass through the shared signed-in account check and selected organization resolver. Independent candidates additionally require the existing candidate learning-access check; the store still verifies ownership of the specific enrollment. There is no author/admin bypass of enrollment ownership. The candidate HTTP fixture uses controlled account/access callbacks; the separate candidate regression proves the existing database-backed account/enrollment access behavior. This is not live-provider acceptance.

The restricted-runtime story integration now exercises real HTTP reads and retry receipts, authentication, locked accounts, candidate access denial, foreign owners, no-store headers, unsupported methods/media types, forged fields and conflicts alongside its transactional store checks. Existing generic HTTP, candidate enrollment/learning/wallet and architecture regressions pass. The initial generic HTTP check was blocked by sandbox localhost EACCES; the permitted rerun passed.

The story publication gate remains. Activity launch, acknowledgement and existing-session/resume paths must all enforce story access before enabling publication. Author and learner UI are also still pending.

## Story activity access (2026-10-30)

A shared in-transaction gate now checks active enrollment/release ownership, current persisted story node, node prerequisites from server facts and release/hash binding before reading acknowledgement, assessment start/get/submit, simulation launch and direct model-session start. Existing model session resume and action submission call the same gate through session access validation. Runtime simulation activity IDs are translated through the published runtime bindings before comparing with the public course activity. Without a saved position, only the story's starting node is considered. Courses without a story retain their existing behavior.

The gate holds a shared enrollment/release lock; accepted story choices require an exclusive enrollment lock, so position cannot advance during the gated activity transaction. For story courses only the current node's activity is actionable. This intentionally prevents reopening old assessment sessions after moving forward; the eventual player must show stored progress summaries rather than reopen those sessions for historical results. Model resume/action denial uses the existing expired-session response without returning model state. Start/acknowledgement/assessment denials use STORY_ACTIVITY_UNAVAILABLE conflicts. Private model-file delivery and reference course text are not restricted by this navigation gate; neither grants completion evidence.

Evidence: restricted-runtime story fixture verifies direct assessment-start/reading skip denial, old reading acknowledgement denial, and completed assessment get/submit denial after advancing to the terminal node. PostgreSQL model rehearsal with --story-access injects a synthetic story into its test release, denies launcher/direct start/resume/action replay from the introductory node, then enters the activity through the real story store and verifies resume. It restores the synthetic manifest before existing lifecycle checks; this is deliberately not an immutable production release modification or publication acceptance. Existing assessment integration, model HTTP and model persistence tests pass, together with build and architecture. The persistence double was updated to return the manifest now required by the shared access query.

Next: no-code authoring, learner navigation/resume UI, story path diagnostics, and end-to-end validation before removing STORY_DELIVERY_UNAVAILABLE. Provider/deployed/device acceptance remains open.

## Learner story navigation (2026-10-30)

The enrollment projection now includes a boolean hasStory without exposing the complete story graph or conditions. The learner page fetches the current server projection before displaying a story course. It shows the mission, node purpose, choice consequences, available choices and only the current activity. Locked nodes show prerequisite guidance. Terminal outcomes explicitly distinguish story completion from certification. Existing recorded progress summaries and the separate certification/wallet flow remain in use.

Choice submission sends only revision and choiceId plus a generated header key. An interrupted response retains that key and disables alternative choices until retry or refresh. Accepted responses trigger a fresh course/story read; the client does not set its own destination. Conflicts disable choices and require refresh. Access loss clears story/activity controls. Generation and identity checks fence late choice responses after navigation or sign-out; sign-out clears retry keys. Heading focus follows accepted navigation and refresh. Story text is inserted as text, never HTML.

The controlled-response Chrome test tools/check-learner-story-browser.mjs verifies current-activity filtering, inert hostile strings, request fields, stable retry identity, conflict refresh, focus, terminal copy, access-loss cleanup and pending-response sign-out. Its --screenshot mode omits the final sign-out exercise to capture the visible player; the default run verifies sign-out. output/learner-story.png was visually inspected at 768px width with an extended viewport to capture all controls. This is synthetic browser coverage, not a real-server story journey or physical-device acceptance. Existing learner browser, non-owner enrollment projection, build and architecture regressions pass.

## No-code story authoring and local preview (2026-10-30)

Controls edit mission, starting node, titles/purposes, activity bindings, narrative-only nodes, choices/destinations/consequences, recorded-result conditions, prerequisites and terminal messages. Untitled activities receive readable numbered labels without changing their stored IDs. Nodes can be added and removed; deleting a starting node or a node with incoming links is blocked until references are changed. Removing choices/nodes/the story requires confirmation. ## Bounded story-path diagnostics (2026-10-30)

Check story paths explores representative completed-result assignments through the production node projector and choice transition function. Facts start incomplete and become available only after reaching an available activity node. This exposes prerequisites that require completion before the activity can start, future-activity dependencies, conditional dead ends, unreached choices/nodes and success/retry/ended outcomes. Every enabled choice is followed, including multiple choices converging on the same destination. Editing the draft clears the report through the existing preview invalidation path.

For scored activities, representatives include zero, one, pass thresholds and configured score thresholds, with failed results and passing results at/above the activity threshold. Counts include one and referenced attempt thresholds up to the configured maximum. Reading acknowledgements produce a completed passing result with score one and one attempt. The failed-at-high-score cases deliberately include simulations whose procedural requirements could fail despite their numerical score. This is hypothetical aggregate evidence, not a proof of attainable assessment scores, actual failure behavior, reset-adjusted retry eligibility, cooldown/review policies, best/latest attempt trajectories or certification. Each scenario assigns one aggregate result per activity; revisits reuse that assignment. Existing personal historical evidence is not assumed.

Analysis is bounded to 128 generated scenarios, 128 reported terminal/blocked paths and 4096 node visits. Complete means all generated representative scenarios and choices were explored without truncation; it is not a proof about every real learner history. When a limit is reached the UI explicitly reports partial analysis, and unreached items mean only not reached in checked cases. Results include exact visited nodes/choices and hypothetical facts without modifying course content or creating evidence.

Tests in tools/check-story-paths.mjs cover pass/retry paths, score gaps, future/self prerequisite blocks, attempt thresholds, reading semantics, deterministic nonmutation and all limits. Integrated author Chrome verifies report/examples alongside the existing story editor, saves, manual preview, conflicts and sign-out. Build and architecture checks pass. An editor write initially failed under the shell's default text encoding; the source was restored using explicit UTF-8 and the author browser regression rerun successfully.

The next required acceptance is a real publication/store/player journey before removing the temporary story delivery gate. Device/provider/deployed acceptance and diagnosis/fault-specific conditions remain open.

## Restart after a retry outcome (2026-10-30)

The learner can confirm Restart mission at an available retry terminal. POST /api/v1/enrollments/{enrollmentId}/story/restart accepts only revision and confirmed:true, with an Idempotency-Key header. The store authorizes the owned active enrollment and exact published release, then atomically moves to the starting node, increments the revision, stores the response receipt and records STORY_RESTARTED. Nonterminal and successful/ended outcomes do not permit restart. Existing assessment results, progress evidence, cooldowns and attempt limits remain unchanged; restarting navigation does not grant another assessment attempt or a credential.

Restart shares the choice receipt namespace. Concurrent identical requests return one receipt and one audit event; changed payloads conflict. Replaying an old restart returns its original receipt without rewinding subsequent progress. Audit failure rolls back navigation. The UI confirms before submitting, retains the same request key after an interrupted response and reloads authoritative position after acceptance.

Evidence: full build, story contract and architecture checks pass. The restricted-runtime PostgreSQL/HTTP fixture verifies confirmation/field validation, terminal-only access, unchanged assessment rows, concurrent replay, audit rollback, one restart audit and old-restart non-rewind. Controlled Chrome verifies cancellation, interrupted-response retry with the same key and authoritative return to the beginning, alongside existing conflict/access-loss/sign-out checks. These are local fixtures, not the real authored-publication journey. Story publication remains blocked until that journey is verified.

## Recorded diagnosis foundation

Simulation state now retains diagnosedFaultIds separately from resolvedFaultIds. Only a successful authoritative diagnosis transition adds the fault; replay cannot duplicate it, and failed resolution retains diagnosis without claiming resolution. New sessions initialize an empty list, and completed simulation progress records include both lists alongside the existing release/model/policy/attempt binding. No client field supplies either list and certification scoring is unchanged.

For legacy persisted state without the new optional field, the next transition derives prior diagnosis from resolved faults and an active fault already in RESOLUTION stage. That derivation follows the existing state-machine invariant that resolution requires accepted diagnosis; it does not infer from client input or free text. Existing stored release/credential records are not rewritten. Persisted explicit diagnosis lists are checked for string entries and duplicates before session restoration.

Pure engine tests cover input nonmutation, diagnosis-versus-resolution distinction, replay, legacy transition and failed-resolution retention. Published local PostgreSQL semantic-action checks verify session and completion payload histories; fault-invalidation checks verify diagnosis-only terminal state and no credential. Full build, architecture, author Chrome and published-story regressions pass. This is evidence capture for E6-T25; story condition schema, selected-attempt projection, author controls and path diagnostics for diagnosis/fault outcomes remain unfinished. In particular an invalidated attempt is not thereby eligible certification evidence.


## Selected-attempt fault fact projection

Server story evidence now includes the published simulation fault IDs and the selected completion payload's diagnosis/resolution lists. The shared best/latest selector chooses the same attempt as certification. Only completed PASSED/FAILED evidence with valid release/policy/model/runtime bindings can produce per-fault diagnosed/resolved booleans. Known optional faults absent from both valid lists produce false; missing legacy payload lists, duplicate/unknown IDs or resolved-without-diagnosed history produce no fault facts, rather than false. An active, expired or invalidated latest attempt also produces no fault facts. Invalidated-session diagnosis remains audit history, not selected completion evidence.

Pure tests verify selection parity, diagnosis-only completed evidence, optional negatives, foreign bindings, malformed/missing histories, duplicate attempts and input nonmutation. PostgreSQL semantic completion verifies real stored history reaches enrollmentStoryFacts and removing the diagnosis field makes fault facts unavailable. Build, architecture, existing story/policy/path and durable story-store regressions pass. course-story:validate includes the new projection tests. No legacy records are backfilled. Author-visible conditions, publication reference validation, preview/path exploration and complete fault-branch journeys remain next for E6-T25; current learner story behavior is unchanged.


## Diagnosis and resolution conditions

Story conditions now accept diagnosed/resolved with activityId, faultId and a boolean equals. Shared context derives fault IDs only from activities explicitly bound to the course simulation definition; assessment/text activities and foreign bindings cannot provide fault references. Publication and runtime story/access validation require a known, unique fault reference. Matching requires a completed activity with exactly one consistent diagnosed/resolved outcome for the requested fault. Missing history cannot satisfy equals:false, and resolved-without-diagnosed evidence is rejected.

Authors can select Fault diagnosed or Fault resolved, choose a fault from the bound simulation, and choose Yes/No. Changing the referenced activity clears the fault selection. Chrome verifies missing-reference feedback, known-fault choices, valid authoring and persistence. Pure tests cover reference context, duplicates, completed-only semantics and missing/ambiguous negative denial.

The --fault-story PostgreSQL rehearsal saves and reviews both conditions, rejects an unknown fault before release creation, publishes, performs real diagnosis/resolution and completes the scored activity. Temporarily absent diagnosis history disables the choice and the store rejects advancement; restored valid history enables the terminal outcome. Full build, architecture, author Chrome, existing story contract and durable store regressions pass. Local preview fault inputs and bounded path exploration remain unfinished, so author preview/path analysis does not yet cover these new conditions. This is local controlled-provider evidence, not deployed/browser-to-server acceptance.


## Fault preview and bounded path exploration

Local story preview now exposes each bound fault as Evidence unavailable, Not diagnosed or resolved, Diagnosed/not resolved, or Diagnosed and resolved. Controls are enabled only for a locally completed activity; returning to Not completed clears its fault history. These facts remain local and create no learner requests or evidence. Existing production story transitions decide whether choices are enabled.

Path analysis validates fault references against simulation activity descriptors and enumerates three consistent recorded states per referenced fault, plus unavailable history. It introduces these facts only when the activity is reached. Resolution without diagnosis is never generated. Cartesian expansion is capped at 128 retained scenarios; counts saturate at Number.MAX_SAFE_INTEGER and report partial coverage when truncation occurs. Existing 128-result and 4096-node-visit limits still apply. Reports display recorded fault outcomes alongside hypothetical score/attempt facts. These combinations test conditional navigation, not simulation attainability or certification eligibility.

Pure path tests cover all three recorded outcomes and missing-history blocks, unknown references, no future evidence, nonmutation, and multi-fault truncation. Integrated Chrome checks unavailable versus diagnosis-only versus resolution choice behavior, clearing history, path-report availability and no learner API requests. Full build, fault projection, architecture and fault-story publication/database rehearsal pass. course-story-faults:validate now runs the full local sequence. Deployed, physical-device and complete accessibility acceptance remain open; this evidence does not establish completion of the full E6 or broader MVP.
