# Candidate model and simulation access

Candidate training contexts now admit model asset requests, learner simulation launch and model-session start/resume/action routes. They use the same active personal-account/issuer/enrollment/release access gate as other candidate learning routes, and the request principal is restricted to learner roles. Session/attempt services continue to bind the actor, enrollment, exact release, activity, definition, model, policy and action sequence.

Model asset delivery now independently requires the requesting actor's ACTIVE enrollment in the exact PUBLISHED release's course version, under organization RLS. This applies to all learner model requests, including organization members. Missing actor or wrong/suspended enrollment returns no asset and creates no download URLs. Author preview remains a separate path.

Learner model responses no longer contain releaseManifestUrl. The complete immutable release artifact includes private content and must not be signed for learner download. The API signs only approved bound model and model-manifest objects. The release hash and release/model/binding IDs remain available for validation; the browser no longer requires the full release URL.

The deployment validator requires `E4_REVIEWED_RELEASE_MANIFEST_PATH`, a local reviewed release JSON artifact supplied through the operator's authorized evidence workflow. It compares that artifact's hash, release-owned storage prefix and model binding against the delivered assets. It does not download the full release through learner credentials. Existing E4 deployment base URL/release/model/token settings remain required as before, and that token must now belong to an actively enrolled learner. Proxy, real storage and provider/device acceptance still need deployment evidence.

Evidence: the PostgreSQL simulation test publishes an actual reviewed synthetic release, seeds an independent candidate acceptance fixture, then checks candidate HTTP launch and semantic actions, private model URL retrieval, no release-manifest URL, foreign-learner rejection and suspension. The rest of the test verifies authoritative completion/resume, invalidation, expiry, retry limits and credential issuance. Candidate acceptance creation is tested separately by the candidate enrollment suite. Storage signing in this test is controlled, and its database connection is the fixture administrator; restricted-runtime candidate assessment/credential tests cover the complementary tenant/role boundary. Model persistence/contract, real Chrome bound-session rehearsal, API binding and the local deployed-validator contract pass. None establishes live Azure deployment acceptance.

Next: browser candidate consent/enrollment and training-context navigation, including preserving invitations/course selection through sign-in where appropriate. Historical cross-issuer wallet access remains a separate open item.
