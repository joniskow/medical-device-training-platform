# Image and video activities

Current status (2026-10-30): approved-media authoring, private learner delivery, rendering and explicit acknowledgement are implemented and locally verified. Valid image/video courses can now publish through normal review, source approval, media schema and certification checks. The saved-draft/publication/delivery/certification rehearsal passes. Earlier sections recording MEDIA_DELIVERY_UNAVAILABLE describe the temporary implementation gate, which has now been removed. Azure streaming, physical-device playback and full video accessibility acceptance remain open.

An image activity has media.assetVersionId and media.altText (nonblank, at most 2000 characters). A video activity has media.assetVersionId and media.transcript (nonblank, at most 100000 characters). Media bindings reject unknown fields and URL-shaped IDs. Supported delivery formats are PNG, JPEG and WebP images, and MP4/WebM videos. An approved asset must have the matching source type and content type. The contract does not claim all codecs or physical devices have been tested, or that a transcript alone completes video accessibility acceptance.

Publication gathers media references independently of AI/source selections and looks up their asset versions inside the tenant transaction. All must be APPROVED; rows are held under a shared lock through publication. The validator receives authoritative source/content types. Media versions participate in the existing source-hash snapshot. Authors cannot provide a URL, blob key or content type inside the binding to bypass these checks. Future delivery must resolve the published version/hash under active enrollment authorization rather than trust client-supplied storage paths.

Evidence: full build, media contract, existing simulation-schema and architecture checks pass. Pure tests cover unknown fields, URL IDs, missing/duplicate approved descriptors, mismatched source/MIME types, description/transcript bounds and nonmutation. Local PostgreSQL publication rejects an unavailable media asset and an approved PDF bound as an image without release/runtime/publication-event records; the restored ordinary course completes publication, simulation and credential lifecycle. Ordinary review/publication regression also passes. These are local fixtures, not deployed media acceptance. Run pnpm media-activities:validate.

## Private learner delivery

GET /api/v1/enrollments/{enrollmentId}/activities/{activityId}/media returns a five-minute private download URL, authoritative content type, lifetime and the published image description or video transcript. It accepts no asset/blob/URL query parameters. Shared account and organization authorization includes independent candidate access. The service requires the learner's active enrollment and a published release, one matching activity, one published source hash, and a currently approved tenant asset with the same hash and matching media type. Storage keys must remain under the tenant prefix. Story courses also enforce current-node access before signing. Shared database locks retain the checked enrollment, release and asset state during URL creation.

The response uses no-store and omits internal storage metadata; storage errors are sanitized. Fetching media records no acknowledgement, score or credential. Previously issued signed URLs can remain usable for their remaining five-minute lifetime after access is revoked; this is bounded URL delivery, not immediate revocation of already issued tokens.

tools/check-media-assets.mjs passes under the local non-owner runtime role for image and video projection, hash/type/source/storage-boundary checks, missing publication snapshots, ownership/tenant denial, enrollment suspension, release retirement, story denial before signing, HTTP account/candidate controls, method/query validation, no-store and safe storage failure. The fixture directly seeds synthetic releases while media publication is blocked, temporarily supplies the missing bootstrap-equivalent story SELECT grant and restores it. It does not test Azure streaming or codecs. Full build, existing HTTP routing and architecture checks pass. Author selection, learner rendering and explicit completion remain next.

## Learner controls and acknowledgement

Image/video activities expose Load media, followed by Refresh media link, plus an explicit Mark as reviewed control after the validated media response arrives. Images have alt text and a visible description; videos use native controls, metadata preload, no autoplay and a visible transcript. Equivalent text is inserted as text, not HTML. Failed playback offers link refresh or the equivalent text; rejected responses clear the previous media and disable acknowledgement. Only HTTPS media URLs without embedded credentials are rendered.

The disposable view removes image URLs and pauses/unloads video on course changes or sign-out. Generation/session checks ignore late responses. Media loading or video playback never automatically records completion. Review submission uses the existing idempotent content acknowledgement transaction, rechecking current story access and the published media asset hash/type/approval. Retained events feed the existing content progress and certification evidence selector; certification still requires scored evidence. Historical acknowledged results remain historical evidence if an asset later becomes unavailable; new acknowledgement requests require current approval.

Full build and architecture checks pass. Controlled Chrome tests verify on-demand controls, inert descriptions/transcripts, explicit acknowledgement and interrupted retry, refresh/error cleanup, unsafe URL rejection and late sign-out disposal. Existing learner and story Chrome regressions pass. The restricted-role database fixture verifies one event from concurrent acknowledgements, no URL signing during acknowledgement, progress projection without private binding disclosure, rejection after asset approval loss and no media-only credential. Browser responses use synthetic URLs and do not prove video codec playback, Azure byte-range delivery or physical-device accessibility. Author media selection and real publication acceptance remain next; MEDIA_DELIVERY_UNAVAILABLE is retained.

## Approved-media authoring

GET /api/v1/approved-media lists up to 50 approved, supported image/video versions in the selected organization with a stable version-ID cursor. It returns only version ID, filename, type and content type, never storage URLs/keys. The route requires the same author/operator/organization-admin permission as draft editing; candidate learner access does not authorize listing. Unknown/duplicate query parameters, malformed cursors and non-GET methods are rejected.

Each module has a paged approved-media picker to add image/video activities with stable activity IDs. Descriptions/transcripts start blank for the author to supply; publication validation requires them. Existing media activities show the bound version, editable description/transcript and a same-type replacement picker. Replacement requires confirmation and retains the activity identity and existing text for explicit review. Additions/replacements use the existing draft autosave pipeline and focus restoration. Picker responses are discarded after removal or identity changes, and filenames are rendered as text. Approval is rechecked at publication and delivery; selecting an asset does not permanently grandfather its approval.

Full build, architecture and generic HTTP checks pass. Integrated author Chrome exercises paged selection, hostile filename rendering, image/video creation, saved accessibility text, replacement type filtering and cancellation/confirmation. Restricted-role PostgreSQL tests cover two pages containing 51 distinct assets, tenant isolation and invalid cursors; HTTP tests deny learner listing and reject unsupported methods/query fields. An initial pagination fixture violated the unique blob-key constraint; each synthetic asset now has a unique key and the expanded test passes. The next acceptance is actual saved-media publication and learner delivery; media publication remains gated.

HTML/static responses now explicitly allow self and HTTPS *.blob.core.windows.net for images and media, including the managed-auth policy override. Script and frame restrictions remain unchanged.

The Chrome regression serves its fixture through createJobStatusHttpServer and verifies browser securitypolicyviolation events: Azure Blob probes are not blocked by image/media directives, while unrelated origins are blocked by each directive. Both managed-auth configurations pass. Probe hosts resolve to loopback and no remote storage is contacted. This verifies browser enforcement of actual response headers, not successful streaming or codec playback. Existing managed-auth configuration and HTTP regressions pass.
